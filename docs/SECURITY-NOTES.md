# 安全基础笔记：加密算法使用场景、代码审计、网络排查

> 这份笔记是自己整理的安全基础，整理原则是**只写能讲清楚、能落到代码上的**。
> 没有实操的部分会明确标注"了解概念"。

## 一、常见加密算法的使用场景

| 类型 | 算法 | 典型场景 | 优点 | 缺点 / 坑 |
|---|---|---|---|---|
| 哈希 | MD5 / SHA-1 | **只用于校验完整性**（老系统） | 极快 | 已被证明碰撞可构造，**禁止用于安全场景** |
| 哈希 | SHA-256 | 文件校验、Git 对象寻址、签名前的摘要 | 快、碰撞不可行 | 不能当密码存储（GPU 每秒可算几十亿次） |
| 口令哈希 | bcrypt / scrypt / Argon2 | 用户密码存储 | 自带 salt、可调计算成本，抗暴力破解 | 慢（这是故意的）；参数选太高会拖垮登录接口 |
| 对称 | AES-128/256-GCM | 大量数据加密（文件、数据库字段、会话内容） | 比非对称快 2~3 个数量级 | 密钥分发难；**必须用带认证的 GCM 模式**，ECB 会泄露明文结构 |
| 非对称 | RSA-2048/4096 | 数字签名、密钥交换、老系统 TLS | 密钥可分公开发布 | 慢；RSA 只能加密小于模长的数据，通常只用来加密对称密钥 |
| 非对称 | ECC / ECDSA / Ed25519 | 现代 TLS、SSH 密钥、签名 | 同等安全强度下密钥短得多、快 | 实现易受侧信道攻击，要用成熟库 |
| 密钥交换 | ECDHE | TLS 前向保密 | 会话密钥泄露不影响历史流量 | 需要正确校验证书链，否则中间人攻击 |
| 编码（不是加密） | Base64 / Hex | 传输二进制（JWT 的 payload 就是 Base64） | 可读、无损耗 | **没有任何保密性**，JWT payload 谁都能解 |

**一句话选型逻辑**：

- 要"不可逆、防篡改" → 哈希（安全场景用 SHA-256 及以上）
- 要"存密码" → 专用口令哈希（bcrypt/Argon2），不是通用哈希
- 要"加密大量数据" → 对称 AES-GCM，密钥用非对称或密钥协商来分发（这就是 TLS 的做法）
- 要"证明身份/不可否认" → 非对称签名

**我在自己项目里的实际应用**：

1. 所有密钥走 `.env` + `.gitignore`，代码里不硬编码 —— 这条是踩过坑才改的（见下）；
2. 所有外部 HTTP 调用走 HTTPS，校验由 `requests` 默认的 CA 证书完成，不关 `verify`；
3. Agent 工具的 `calculator` 用**字符白名单**代替裸 `eval`，把"能执行任意 Python"降级成"只能算四则运算"。

## 二、代码审计练习笔记

### 2.1 密钥硬编码（自己犯过的真实问题）

早期把 API Key 直接写在 `1.py` 里，`llm = ChatOpenAI(api_key="sk-...")`。
**只要这个文件进了 Git，密钥就等于公开**（即使后来删掉，历史提交里还在）。
正确做法：`.env` + `os.getenv()`，`.env` 加入 `.gitignore`，另提供 `.env.example`。
本仓库已全部改造，历史文件里不再有任何真实密钥。

### 2.2 危险函数与输入校验

| 风险点 | 危险写法 | 修法 |
|---|---|---|
| 命令注入 | `os.system("ping " + host)` | 用 `subprocess.run([...], shell=False)`，参数列表传参 |
| 代码注入 | `eval(user_input)` | 白名单校验 / `ast.literal_eval` / 用解析器 |
| 反序列化 | `pickle.load(不可信文件)` | 换 JSON；必须用 pickle 时校验来源与签名 |
| 路径遍历 | `open(base + user_path)` | `Path.resolve()` 后校验是否仍在 base 目录内 |
| SSRF | 服务端帮用户请求任意 URL | 白名单域名 + 禁止内网网段（127.0.0.1/10./172.16/192.168/169.254） |
| SQL 注入 | 字符串拼 SQL | 参数化查询（`cursor.execute(sql, params)`） |

### 2.3 审计时我习惯先看的入口

1. 所有接收外部输入的地方：HTTP 路由参数、上传文件名、请求头；
2. 所有"把输入拼进别的东西"的地方：SQL、shell、文件路径、模板；
3. 所有配置和日志：有没有把密钥、token、身份证号打进日志；
4. 依赖：`pip list --outdated` / `npm audit` 看已知漏洞版本。

## 三、网络排查笔记

### 3.1 分层定位思路

出了"连不上"，从下往上一层层排，不要一上来就怀疑代码：

```
链路层/网卡   → ipconfig / ifconfig，看有没有拿到 IP
IP/路由      → ping 网关、ping 8.8.8.8（判断是 DNS 还是路由问题）
DNS         → nslookup 域名（能不能解析出 IP）
端口/传输层   → telnet ip port / Test-NetConnection（端口通不通）
应用层       → curl -v（看 HTTP 状态码、请求头、证书）
```

常用工具：`ping` / `tracert` / `nslookup` / `netstat -ano` / `curl -v` / `telnet` /
Wireshark（抓包看真实报文）/ mitmproxy（HTTP 代理，看请求响应细节）。

### 3.2 TCP/IP 里我实际用到的点

- **三次握手**：`curl -v` 卡在 "Trying..." 通常是 SYN 没回（防火墙/安全组），
  卡在 "Connected" 之后才是应用层问题；
- **端口与监听**：`netstat -ano | findstr :7860` 看 Gradio 到底起没起、被哪个 PID 占了；
- **局域网互联**：同一网段用私有地址（192.168.x.x），跨网段需要网关和路由表；
  服务要监听 `0.0.0.0` 而不是 `127.0.0.1`，Windows 防火墙要放行端口。
- **HTTP 状态码语义**：401（认证失败）/ 402（欠费）/ 403（无权限）/ 429（限流）/
  5xx（服务端问题）—— 区分清楚能省大量排查时间。我在多模态 Agent 里就专门对 402 做了提示。
